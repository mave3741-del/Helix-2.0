Helix 2.0 — AI Organization OS

1 Owner · 1 CEO · 1,000 persistent workers · private repo github.com/mave3741-del/helix

1. Executive summary

Helix is a production-grade organizational operating system, not a chatbot and not a collection of independent agents. One human Owner directs one CEO. The CEO runs executive management, twelve departments, supervisors, and exactly 1,000 persistent AI workers, with independent QC, testing, security, skill creation, organizational memory, model routing, fallback, governance, audit, and recovery.

Central principle. The organization is the intelligence. Models are replaceable brains. Helix stays operational if a worker, model, provider, skill, or workflow fails.

2. What Helix is (and is not)

Helix isHelix is not
An Owner dashboard plus an autonomous operating layerA chat UI wrapping one model
Persistent worker identities with history1,000 simultaneous LLM processes
Hierarchical coordinationA swarm of peer agents
Independent QC / testing / securityA worker judging its own output
Memory owned by the organizationSession context that dies with a model

The Owner talks to the organization. The Owner is not required to manage individual workers.

3. Architecture

OWNER (human)
  └── CEO  (Helix CEO, Grok 4.5 strategy brain)
        ├── 8 executives
        ├── 12 department managers
        ├── supervisors / 48 teams
        ├── 1,000 persistent workers (W-0001 … W-1000)
        ├── QC / testers / security / recovery
        └── OmniRoute  →  brains + fallback chain

Core loop

  1. Owner issues an objective (or a scenario injects one).
  2. Risk is classified: low / medium / high. High-risk work stops for Owner approval.
  3. CEO sets strategy and selects departments.
  4. Managers / supervisors assemble teams from the 1,000-worker registry.
  5. Workers execute. Supervisors review. Independent QC checks. Testing validates.
  6. Failures enter diagnosis → correction → retest.
  7. Verified lessons become memory. Skills go sandbox → test → approve → deploy.
  8. A 420ms tick advances queues, tasks, QC, training, fallback, succession, and KPIs.

Worker identity, worker state, worker process, model session, and task execution are separate. All 1,000 identities persist in IndexedDB. Restart restores the last checkpoint.

5. Quality, learning, and skills

Quality gates: requirement verification → worker self-check → supervisor review → independent QC (different brain from the author) → testing → security / risk review → final verification → delivery.

Memory layers: organization, department, team, worker, task, project. Claim status: verified, unverified, rejected, superseded, under review. Rejected information does not become trusted knowledge.

Skills are created when a capability is missing: sandbox → test → security → QC → approve → deploy, with version and rollback. Untested skills stay in sandbox.

6. Brains (models)

All five brains start available.

Fallback chain: Grok 4.5 → Grok Fast → Cloud Coder → Open Reasoner → Local Heuristic. Switching brains does not reset the task. Brain failure is not organizational failure.

7. Governance

Fifteen constitution rules cover Owner authority, verified results, no unverified facts, correction cycles, replaceable brains, model-independent memory, tested skills, auditability, high-impact approval, controlled self-improvement, security boundaries, task continuity, and evidence over claims. High-risk work requires Owner approval. Emergency halt pauses the organization. Recovery restores from checkpoint.

8. Owner interface

Command, Organization, Workforce, Work, Quality, Brains, Skills, Memory, Governance, Improve, Prove. Desktop rail plus mobile bottom navigation. Pause, resume, recover, and emergency halt are Owner controls.

  5. Open Brains — all five models start available.
  6. Open Prove and run all fourteen tests.
